## 1. Clean-Room Boundary & Core Principles
This specification suite adheres to a strict **clean-room specification process** to ensure that all documentation in `spec/` and downstream software implementations remain completely unencumbered by vendor copyrights and proprietary trade secrets.

```
+-------------------------------------------------------------+
|               OBSERVATION & PROTOCOL ANALYSIS              |
|  - Hardware interface probing & bus telemetry               |
|  - Live network packet capture & socket state analysis       |
|  - Storage layout mapping & runtime filesystem diffing      |
|  - Autonomous protocol synthesis & clean abstraction        |
+-------------------------------------------------------------+
                              |
                              | Synthesis & Functional Abstraction
                              | (Observable behaviors, framing, wire formats)
                              v
+-------------------------------------------------------------+
|                  CLEAN SPECIFICATION (spec/)                |
|  - Protocol state machines, packet layouts, field tables     |
|  - RFC 2119 normative constraints                           |
|  - Claim confidence tagging (confirmed, static, inferred)   |
|  - Independent test vectors synthesized from clean inputs    |
|  - Explicit unknown markers; ZERO keys / ZERO vendor code   |
+-------------------------------------------------------------+
                              |
                              | Independent Implementation
                              v
+-------------------------------------------------------------+
|                      CLEAN IMPLEMENTER                      |
|  - Independent developer or tool author                     |
|  - Reads ONLY public spec/ documentation                    |
|  - Never inspects vendor proprietary software or raw keys   |
|  - Clarifying questions flow via public Q&A tracking        |
+-------------------------------------------------------------+
```

### 1.1 Prohibited Content (Dirty-Room Contamination)

The following materials are **STRICTLY PROHIBITED** from appearing anywhere in `spec/`:

1. **Vendor Source Code or Decompiled Output:**
   - No decompiled C/C++, assembly listings, or pseudocode snippets generated by Ghidra, IDA Pro, Binary Ninja, or other decompilers.
   - No vendor variable names, internal function names, class names, or type identifiers unless they are literal tokens transmitted verbatim over the wire or stored in binary headers.
   - No comments or text copied from vendor binaries, firmware scripts, or vendor software.

2. **Proprietary Keys, Certificates, and Secrets:**
   - No cryptographic keys, private certificates, initialization vectors, passphrases, or secret seed values.
   - No hex dumps or raw byte arrays containing vendor cryptographic material.
- No SHA-256 fingerprints of secret keys or vendor proprietary certificates.

3. **Internal Firmware & Device Dumps:**
- No internal filesystem paths pointing to private analysis directories, raw flash image dumps, carved partition files, or vendor installer directories.
   - Target controller runtime paths (e.g., `/remote/Store/updateroot/`) are permitted only when describing target directory contracts required for network staging or file placement.

4. **Proprietary Vendor Assets:**
   - No proprietary IR databases, serial driver codes, artwork, UI templates, fonts, or copyrighted graphic assets.

### 1.2 Permissible Content (Clean-Room Interoperability)

All documentation in `spec/` MUST be authored in original language and MUST be restricted to:

- Wire protocols, packet headers, framing formats, and socket communication sequences.
- Network ports, transport requirements (TCP, UDP, TLS), and discovery broadcasts.
- Binary and text file formats, container headers, chunk structures, and schema layouts.
- Magic numbers, opcodes, protocol command tokens, and status codes required for interoperability.
- Finite state machines, controller lifecycle sequences, timeouts, and error handling behaviors.
- Test vectors generated from clean, independently authored inputs with deterministic expected outputs.

### 1.3 Legal & DMCA §1201 Compliance

Interoperability research is conducted under the protections of United States copyright law, fair use for interface specification, and the statutory interoperability exception of the Digital Millennium Copyright Act (17 U.S.C. § 1201(f)).

Sections describing container decryption, key application, or communication session encryption carry potential DMCA §1201 trafficking implications. Such sections MUST declare `circumvention: true` in their frontmatter and require formal legal verification prior to public distribution.


### 1.4 Protocol Verification & Analysis Methodology

To discover and verify the protocols, data structures, and operational semantics specified across `spec/` without reliance on proprietary vendor source code or internal development manuals, authors employ a multi-layered interoperability methodology:

1. **Hardware Interface Probing & Serial Console Telemetry:**
   - Physical examination of the controller mainboard PCB, identifying the core SoC, power management IC, volatile memory, flash storage, Ethernet transceiver, and hardware co-processors.
   - Non-destructive bench probing of hardware test points, validating logic voltage levels across passive test points.
   - Passive observation of serial console output to catalog bootloader milestones, kernel boot parameters, and hardware initialization sequences.

2. **Storage Layout & Filesystem Architecture Mapping:**
   - Mapping of storage partitions, file hierarchies, and directory structures across `/remote/Store`.
   - Cryptographic hashing (SHA-256) of observed configuration files to ensure exact byte-level verification.
   - Analysis of runtime initialization scripts to map system runlevels, service ownership, and persistent mount points.

3. **Interface & Protocol Model Synthesis:**
   - Systematic cataloging of listening ports, wire framing formats, and protocol command dispatchers.
   - Algorithmic reconstruction of state machines, request/response sequences, and error handling routines based on observable wire and database artifacts.
   - Dynamic correlation of socket endpoints with owning system services.

4. **Dynamic Network Telemetry & Socket Mapping:**
   - Socket-to-process correlation across active hardware: resolving every listening port and bound datagram socket to its functional system daemon.
   - Network traffic capture using standard packet capture utilities, analyzing packet traces during discovery, staging, and activation cycles.
   - Controlled network query injection against service endpoints to evaluate protocol corner cases, status replies, and checksum validation routines.

5. **State Diffing & Differential Analysis:**
   - Systematic filesystem state snapshotting before, during, and after configuration staging, software reload triggers, and hardware reboots.
   - Tracking installed databases and staging manifests to verify migration paths and runtime daemons.

6. **Clean Model Synthesis & Round-Trip Validation:**
   - Independent reconstruction of data formats (databases, automation tables, upload manifests, container headers) using clean reference parsers and generators.
   - Byte-exact round-trip verification against reference test fixtures, confirming byte preservation and structural layout fidelity for tested schemas.

## 2. Document Frontmatter Specification

Every specification document in `spec/` (e.g., `spec/00-system-overview.md`, `spec/20-upload-manifest.md`) MUST begin with a YAML frontmatter block adhering to the following schema:

```yaml
---
title: "Document Title"
section: "NN-section-slug"
version: "0.1.0"
status: draft | review | ratified | deprecated
circumvention: false | true
---
```

### 2.1 Frontmatter Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `title` | `string` | **Yes** | Human-readable title of the specification section. |
| `section` | `string` | **Yes** | Canonical section identifier matching the filename without extension (e.g., `00-system-overview`, `10-storage`, `20-upload-manifest`, `30-tmc2-container`). |
| `version` | `string` | **Yes** | Semantic version of the document (`MAJOR.MINOR.PATCH`). Increment `PATCH` for clarifications, `MINOR` for substantive additions, and `MAJOR` for breaking interface revisions. |
| `status` | `enum` | **Yes** | Lifecycle status of the specification: <br>• `draft`: Initial composition in progress; known omissions.<br>• `review`: Structurally complete; awaiting empirical peer review or test vector verification.<br>• `ratified`: Empirically validated against real hardware or emulation; stable.<br>• `deprecated`: Obsoleted by newer protocol versions or hardware revisions. |
| `circumvention` | `boolean` | **Yes** | **REQUIRED.** Set to `true` if the section details decryption, key unmasking, or bypassing vendor container protections. Set to `false` for standard protocols and unencrypted data layouts. |
| `evidence` | `list of strings` | No | Optional list of external validation references or RFC citations. |

## 3. Normative Language (RFC 2119 / RFC 8174)

Specifications in `spec/` MUST use the normative terminology defined in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt) and [RFC 8174](https://www.ietf.org/rfc/rfc8174.txt). When capitalized, these terms convey precise conformance requirements:

- **MUST / SHALL / REQUIRED:**
  Absolute requirement. An implementation that fails to satisfy this criterion is non-conformant and will fail interoperability.
- **MUST NOT / SHALL NOT:**
  Absolute prohibition. An implementation that performs this action is non-conformant.
- **SHOULD / RECOMMENDED:**
  Strong recommendation. Valid reasons may exist in particular circumstances to ignore this item, but the full implications MUST be understood and carefully weighed before choosing a different course.
- **SHOULD NOT / NOT RECOMMENDED:**
  Strong prohibition. Valid reasons may exist in particular circumstances when the behavior is acceptable, but the full implications MUST be understood and carefully weighed before choosing this course.
- **MAY / OPTIONAL:**
  Truly discretionary item. An implementation that includes the option MUST interoperate seamlessly with another that omits it.

Spec authors MUST use these terms strictly to define protocol requirements, avoiding passive voice or ambiguous recommendations.

## 4. Spec Section Definition of Done (DoD)

To achieve `status: ratified` (or complete a roadmap milestone targeting `spec/`), each specification document MUST satisfy the following six-point Definition of Done:

### 1. Complete Field Layout Tables
Every structured binary frame, header, configuration file, or message MUST have a comprehensive field table with explicit columns:
- **Offset / Order:** Byte offset (hex or decimal) from structure start, or sequential token index.
- **Field Name:** Descriptive, clean-room field name (e.g., `magic_header`, `payload_length`, `checksum`).
- **Data Type:** Exact primitive type (e.g., `uint8`, `uint16_le`, `uint32_be`, `int32_le`, `char[16]`, `utf8_string`).
- **Size:** Byte or bit length.
- **Endianness / Encoding:** Explicit endianness (`Big-Endian`, `Little-Endian`) or string encoding (`ASCII`, `UTF-8`, `NUL-terminated`).
- **Allowed Values / Range:** Permitted enumerations, bitmasks, or boundaries.
- **Description:** Clear functional purpose.
- **Explicit Unknowns:** Unknown or unmapped fields MUST NOT be silently omitted. They MUST be designated as `Unknown / Reserved`, documenting the observed default value (e.g., `Always 0x00`, `Observed values: 0x01, 0x02`).

### 2. Semantics & Controller Behavior
- Detailed breakdown of what the controller executes, expects, and produces for each message or field.
- Explicit lifecycle transitions, finite state machine (FSM) models, message ordering constraints, timeout limits, and default parameter fallbacks.

### 3. Error Behavior & Edge Cases
- Exhaustive documentation of controller response to anomalous input: malformed headers, invalid checksums, truncated payloads, unexpected sequences, or buffer overruns.
- Clear statement of failure modes (e.g., TCP connection reset, NAK frame, silent packet drop, log record, controller daemon restart).
- Any unverified error condition MUST be cataloged in the Open Items section.

### 4. Test Vectors
- At least one reproducible, clean test vector generated purely from independent inputs with deterministic expected results.
- Concrete hexadecimal byte streams or structured payloads accompanied by intermediate calculation values (e.g., CRC-32, MD5, AES-CBC ciphertext).
- Validated against the live controller or emulator whenever feasible.

### 5. Claim Confidence Categorization
Every protocol statement, field definition, or operational claim MUST be explicitly categorized by confidence:
- **`[CONFIRMED]`**: Empirically validated via live network packet capture, hardware stimulus, or emulated execution with observed I/O.
- **`[STATIC]`**: Deduced from static binary analysis, string table inventories, or static file layouts without live runtime verification.
- **`[INFERRED]`**: Deduced from architectural context, protocol conventions, or domain analogies. Carries residual uncertainty and requires empirical validation.

Every claim is tagged with its empirical verification level (`[CONFIRMED]`, `[STATIC]`, or `[INFERRED]`).

### 6. Open Items Section
- Every specification document MUST conclude with an explicit "Open Items" section.
- Gaps, pending hardware tests, and unmapped fields MUST be enumerated with clear problem statements and proposed verification methods.
- A roadmap milestone may be completed with open items only if none of the open items block downstream programmer staging or core controller communication.

## 5. Key & Secret Handling Rule

A foundational principle of this project is that **no proprietary cryptographic key, certificate, or secret ever appears in `spec/`**:

1. **Zero Key Material:**
   - Never write raw key bytes, hexadecimal key representations, private certificates, or cryptographic secrets into `spec/`.
   - Never write key fingerprints or key hashes into `spec/`.

2. **Abstract Declaration:**
   - When a protocol or container requires cryptographic operations, state only that a key is required.
   - Detail the algorithm, cipher mode, key size, and initialization vector parameters (e.g., "The container payload is encrypted using AES-128-CBC. A 128-bit symmetric key and 16-byte IV are required to decrypt this section.").

3. **Frontmatter Flag:**
   - Any document detailing encrypted structures or key-dependent operations MUST specify `circumvention: true`.

4. **Mandatory External Key Provisioning for Implementations:**
   - `spec/` MUST NOT distribute or publish proprietary vendor keys.
   - Compliant third-party software, compilers, or tools implementing this specification MUST NOT embed, bundle, hardcode, or automatically download proprietary vendor keys, secrets, or certificates.
   - Any tool requiring cryptographic operations MUST mandate runtime external key injection:
     - The end-user MUST explicitly supply necessary keys at runtime via an environment variable (e.g., `URC_KEY_HEX`) or a local configuration file (`--key-file /path/to/key.bin`).
     - If a required key is not provided by the user at runtime, the tool MUST exit gracefully with an informative diagnostic prompt requesting user configuration, without attempting fallback to hardcoded or remote-fetched secrets.

## 6. Interaction with `spec/questions.md`

When clean-room implementers encounter ambiguities, omissions, or apparent contradictions while developing software against `spec/`:

1. **Logging Inquiries:**
   - Implementers log questions into `spec/questions.md` using the standardized Question Schema.
   - Questions MUST be framed strictly in terms of observed behavior and specification text. Implementers MUST NOT request vendor source code, decompiled routines, or dirty-room artifacts.

2. **Research & Synthesis:**
   - Specification authors investigate the inquiry using hardware testbenches, network captures, or protocol verification.
   - Findings are abstracted and written strictly in clean-room normative terms.

3. **Specification Feedback Loop:**
   - The primary deliverable answering a question is an update to the corresponding `spec/*.md` document, with an appropriate version bump.
   - `spec/questions.md` is updated with a concise clean summary and a reference to the resolving commit or specification revision. Answers are never communicated out-of-band.

## 7. Standard Spec Section Template

Spec authors SHOULD use the following template when creating a new specification document:

````markdown
---
title: "Section Title"
section: "NN-section-slug"
version: "0.1.0"
status: draft
circumvention: false
---

# Section Title

## 1. Overview
High-level description of the interface, container format, or protocol.

## 2. Protocol / Format Specification

### 2.1 Message Framing / Header Layout
Description of framing and byte layouts.

| Offset | Field Name | Type | Size | Endianness | Allowed Values | Description |
|---|---|---|---|---|---|---|
| 0x00 | `magic` | `uint32` | 4 bytes | Big-Endian | `0x55524331` ("URC1") | Protocol header magic [CONFIRMED] |
| 0x04 | `version` | `uint16` | 2 bytes | Big-Endian | `0x0001` | Protocol version [CONFIRMED] |
| 0x06 | `reserved` | `uint16` | 2 bytes | N/A | `0x0000` | Unknown / Reserved. Observed value 0x0000 [STATIC] |
| 0x08 | `payload_len` | `uint32` | 4 bytes | Big-Endian | `0 - 65535` | Payload byte length [CONFIRMED] |

### 2.2 Semantics & Controller Behavior
Detailed state machine, message sequencing, and controller reaction to fields.

## 3. Error Handling & Edge Cases
Controller behavior when encountering truncated data, bad checksums, or unexpected messages.

## 4. Test Vectors
Deterministic input vectors with expected outputs.

### Test Vector 1: Standard Frame
- **Input:** `00000000: 5552 4331 0001 0000 0000 0004 0102 0304`
- **Expected Processing:** Accepted; dispatches payload `01 02 03 04`.

## 5. Open Items
- [ ] Determine behavior if `payload_len` exceeds 65535 bytes.
- [ ] Confirm timeout duration on dropped connection.
````
